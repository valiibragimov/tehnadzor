# Политика безопасности

Исправления безопасности принимаются для ветки `main`. Отдельной поддерживаемой линейки релизов нет.

## Как сообщить об уязвимости

Не публикуйте детали эксплуатации и конфиденциальные данные проектов в открытых issues. Если доступен приватный контакт разработчика, используйте его. Если такого контакта нет, создайте короткий issue с вопросом, как передать сообщение, без подробностей воспроизведения, раскрывающих действующую систему.

В приватном сообщении опишите затронутый компонент, последствия, ожидаемое поведение и шаги воспроизведения на синтетических данных. По возможности приложите безопасный пример запроса или тестовых данных.

Не прикладывайте учётные данные, cookies, токены, файлы сервисных аккаунтов, приватные ключи, персональные данные, адреса объектов, договоры, сметы и закрытые IFC-модели.

## Конфигурация и данные

Локальные `.env` и учётные данные Firebase Admin не должны попадать в систему контроля версий. Используйте файлы `.env.example` из репозитория только как справочник имён параметров. Храните данные сервисных аккаунтов в защищённых локальных файлах или хранилище секретов окружения.

Веб-конфигурация Firebase включается в браузерную сборку. Её API key идентифицирует проект и не является учётными данными Admin. Он не заменяет правила Firestore, ограничения Authentication и подходящую настройку App Check.

Прежде чем открыть доступ к экземпляру приложения, проверьте аутентификацию API, права доступа к проектам, ограничения CORS и частоты тяжёлых операций. Логи не должны содержать токены, тела файлов и персональные данные. Рассматривайте [правила Firestore](firestore.rules) вместе с [требованиями к публикации данных](docs/bim.ru.md#публикация-моделей): Admin SDK обходит правила.

Для проверок используйте отдельный Firebase-проект для разработки или изолированный эмулятор. Скриншоты и примеры моделей должны быть синтетическими или обезличенными.
