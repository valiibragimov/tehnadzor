# Архитектура

Tehnadzor — модульный монолит на TypeScript. Браузер, Express API и Firebase Function работают отдельно. Общая инженерная логика и код публикации моделей не зависят от их интерфейсов и реализаций хранилища.

## Ответственность компонентов

| Область | Ответственность |
| --- | --- |
| [Клиент](src/client) | Сборка рабочей области, инженерные формы, навигация по проектам и представление данных |
| [Модули проверок](src/client/features/inspections) | Оценка замеров, состояние модулей и сценарии проверок |
| [Клиентские репозитории](src/client/app/repositories) | Доступ к Firestore и контракты хранения |
| [Прикладной слой сервера](server/src/application) | Правила импорта через внедряемые интерфейсы разбора и хранения |
| [Серверная инфраструктура](server/src/infrastructure) и [репозитории](server/src/repositories) | Firebase Admin и адаптеры хранения |
| [Серверные workers](server/src/workers) | Разбор IFC с нагрузкой на CPU, без записи в Firestore |
| [Общие BIM-модули](src/shared/bim) | Инженерные данные, преобразование сущностей WebIFC и правила публикации моделей |
| [Functions](functions/src) | HTTP-функция новостной ленты профиля |

Firebase Authentication определяет пользователя. Доступ браузера к Firestore регулируют [правила](firestore.rules). API проверяет токены и принадлежность проекта пользователю до обращения через Admin SDK, который обходит эти правила.

Клиент связывает модули через явно переданный контекст рабочей области. Каждый модуль управляет своим изменяемым состоянием и предоставляет публичный API. Инженерные расчёты должны оставаться независимыми от DOM и Firebase. В некоторых старых модулях эти обязанности ещё совмещены; повторять такой подход в новом коде не следует.

## HTTP-контракт

Валидаторы запросов находятся в [server/src/http-contract.ts](server/src/http-contract.ts). Генератор формирует [api/openapi.json](api/openapi.json), общие декларации TypeScript и идентификаторы маршрутов. Клиент использует эти контракты через `openapi-fetch`.

После изменения контракта:

```sh
npm run api:generate
npm run api:check
```

Не редактируйте сгенерированные API-файлы вручную. Клиентские HTTP-вызовы используют аутентификацию и ограничение времени ожидания. Формирование отчётов находится в [server/src/presentation](server/src/presentation) и отделено от HTTP-обработчиков и хранения. Отчёты собираются из структурированных результатов проверок.

## Обработка IFC и хранение

Единый [адаптер WebIFC](src/shared/bim/ifc-model.ts) преобразует IFC-сущности в общие инженерные данные. Он выполняется в браузерных Workers и ограниченном серверном пуле Piscina. Сетевые операции и работа с Firestore остаются вне workers разбора.

Отображение реализовано отдельно: Three.js и IFC-Lite строят интерактивную сцену. Отображаемая геометрия не служит достоверным источником проектных размеров. Просмотрщик перерисовывает сцену по необходимости и при закрытии освобождает ресурсы парсера и WebGL.

Оба адаптера хранения используют [publication.ts](src/shared/bim/publication.ts). Импорт сначала записывает неизменяемое поколение данных, затем транзакционно публикует манифест. Страницы с курсором и продлеваемые аренды чтения сохраняют согласованность снимка каталога при одновременном импорте и очистке. Старые записи доступны до замены или явного скрытия; автоматического переноса данных нет.

В [документе о BIM и IFC](docs/bim.ru.md) описаны модель данных, конкурентный доступ, очистка и ограничения координат.

## Интерфейс

UI использует нативные HTML-элементы и общие обработчики на TypeScript. На desktop навигация расположена в боковой панели, на мобильных устройствах — внизу. Панели проверок используют нативные диалоги, справка — Popover API.

В [liquid-glass.css](liquid-glass.css) находятся семантические токены и общие компоненты слоя каскада `design`. Имя файла сохранено как публичный путь к ресурсу. [style.css](style.css) содержит старые компоновки в слое `legacy` с меньшим приоритетом. Расширяйте существующие компоненты, не добавляя очередную таблицу стилей с переопределениями.

Переводы интерфейса хранятся в [словарях i18next](src/client/shared/i18n). Смена языка не должна менять сохранённые значения конструкций, идентификаторы, оси и нормативные обозначения. Часть пояснений к результатам и текстов отчётов остаётся на русском.

## Исходники и генерируемые файлы

[Структура клиента](src/client/README.ru.md) объясняет назначение модулей и переходных каталогов. [Скрипты сборки](scripts/README.ru.md) описывают генерируемые файлы. В [руководстве по разработке](docs/development.ru.md) приведены команды и требования к окружению.

Общие декларации публикации генерируются командой `npm run shared:generate`; `npm run shared:check` проверяет их соответствие исходникам. Проверки API и общих деклараций входят в сборку клиента.

## Известные ограничения

Серверная очередь работает в одном процессе и привязана к запросу. Брокера с сохранением заданий и планирования между экземплярами приложения нет. Firestore читается постранично, но клиент хранит полный каталог метаданных; геометрия не загружается потоково. Для проверки памяти и полноты поддержки формата ещё нужны большие модели и примеры от разных IFC-экспортёров.

В старых модулях остаются прямые вызовы Firebase и прежний CSS. Обновление браузерного хранилища также нужно проверять на staging с кешами от ранее развёрнутых клиентов. Изменения в этих областях должны сохранять записи и проходить проверку затронутого пользовательского сценария.

Инженерные правила и требования к изменениям находятся в [AGENTS.md](AGENTS.md) и [руководстве для участников](CONTRIBUTING.ru.md).
