# BIM и IFC

IFC дополняет проверки сведениями об элементах, их расположении и доступными проектными значениями. Импорт и 3D-отображение — разные процессы: наличие формы в просмотрщике ещё не означает, что из неё можно извлечь инженерные размеры.

## Импорт

[src/shared/bim/ifc-model.ts](../src/shared/bim/ifc-model.ts) — общий адаптер WebIFC. WebIFC разбирает STEP-сущности и ссылки. Адаптер преобразует их в [инженерные записи](../src/shared/bim/types.ts), приводя длины и координаты к миллиметрам.

Один и тот же адаптер выполняется в браузерном Worker и серверном пуле Piscina. Серверный API принимает байты IFC без дополнительной упаковки; запросы и ответы описаны в [OpenAPI](../api/openapi.json). Ограничены размер входных данных, число сущностей, очередь и время выполнения. Для импорта метаданных GPU не нужен.

Для проверок поддерживаются плиты, колонны, стены, балки и лестницы. Записи могут содержать:

- Стабильный идентификатор элемента, ID исходной модели и IFC GUID.
- Марку, оси и этаж, если эти сведения есть в исходных данных.
- Проектные X, Y и отметку из поддерживаемых цепочек размещений.
- Заданные размеры: толщину, ширину, высоту и размеры сечения.

Отсутствующие или неподдерживаемые значения остаются `null`. Размеры не оцениваются по габаритам отображаемой геометрии. Геодезические и геометрические формы используют поддерживаемые координаты и размеры; проверки армирования и прочности сохраняют привязку к элементу, не придумывая измерения.

Сохранённая проверка содержит снимок BIM-привязки. Удаление или замена модели не удаляет исходные результаты проверки, хотя ссылка может стать недоступной в текущем каталоге.

## Координаты и поддержка формата

Адаптер учитывает единицы длины проекта и свойств, вложенные преобразования локальных размещений, наборы свойств и связи с этажами. Некорректные кортежи координат отклоняются, а не исправляются эвристически.

Тесты проверяют совпадение результатов разбора в браузере и Node, представления Body и Axis, вложенные повороты с большими координатами, mapped geometry и тела с булевыми операциями. Размеры mapped geometry и булевых тел остаются неизвестными, если их извлечение не поддерживается.

IFC Grid/LinearPlacement, MapConversion, сложные структуры свойств и размеры некоторых тел с тесселяцией поддержаны не полностью. Нельзя считать, что импортированные координаты учитывают все преобразования геопривязки конкретного экспортёра. Сверяйте критичные значения с проектной моделью.

Старый тестовый файл коттеджа содержит некорректные кортежи с десятичными запятыми и сохранён для диагностики. Тесты просмотрщика используют корректные синтетические модели; они не подтверждают полную совместимость со всеми реальными экспортёрами.

## Публикация моделей

Общие [правила публикации](../src/shared/bim/publication.ts) используют браузерный и Admin-адаптеры хранения.

1. Зарегистрировать поколение и записать его элементы ограниченными пакетами.
2. Проверить ожидаемое число элементов и транзакционно опубликовать версионированный манифест.
3. Сравнить ревизии моделей и эпохи проекта, чтобы запоздавший импорт не заменил более новые данные и не восстановил удалённую модель.
4. Сохранить неизменяемую запись об успешной публикации с поколением и ожидаемым числом элементов.

В новой схеме внутри проекта хранятся манифесты `bimModels`, реестр `bimGenerations` и записи публикаций `bimPublications`. Старые `elements` остаются доступны до замены модели или явного скрытия. Неизвестная версия манифеста блокирует чтение.

Чтение идёт страницами не более 200 элементов. Читатель получает ревизию каталога и продлеваемую пятиминутную аренду `bimReaders`, закрепляющую неизменяемые поколения. Публикация, получение аренды и сборка мусора согласуются через корневую ревизию. Продление обновляет только собственную аренду читателя. Если аренда истекла и поколение уже удалено, чтение блокируется.

Для этого протокола браузер читает данные с сервера, без подстановки кешированных результатов запросов. Между модулями используется один неизменяемый каталог проекта. Это исключает дублирование каталогов, но память всё ещё растёт с числом элементов. Списки выбора отображают не более 100 совпадений, выполняя поиск по всему каталогу.

## Очистка и восстановление

Очистка запускается отдельной командой обслуживания; фонового расписания в развёрнутой системе нет. Заменённые поколения сохраняются 24 часа после вывода из использования, незавершённые импорты — один час после последнего heartbeat.

После `npm run build:server:ts` можно посмотреть состояние реестра для явно выбранного **тестового** проекта:

```sh
npm run bim:gc -- --firebase-project YOUR_TEST_FIREBASE_PROJECT --project YOUR_TEST_PROJECT_ID
```

По умолчанию команда только читает данные: выводит число записей по статусам и настройки хранения, а не точный список будущих удалений. Вне эмулятора она использует Application Default Credentials. Для эмулятора нужны loopback-адрес и ID Firebase-проекта с префиксом `demo-`.

Параметр `--apply` запускает сборку мусора и удаляет блоки подходящих поколений. Сборщик транзакционно перепроверяет ревизию координации и аренды читателей, блокирует запись продолжающихся импортов и помечает поколение как удаляемое до удаления ограниченных порций данных. Прерванную очистку можно продолжить.

Записи об успешной публикации и отметки об удалённых поколениях остаются для диагностики. Запись о публикации не позволяет восстановить уже удалённые блоки. Для восстановления нужно выбрать успешную публикацию, проверить наличие полного поколения и опубликовать его заново. Для возврата к старому механизму чтения сначала нужно записать выбранный снимок в `elements`; автоматического отката нет.

Незарегистрированные поколения намеренно сохраняются. До их регистрации нужно остановить старые Admin-процессы записи и проверить записи успешных публикаций. Admin SDK обходит правила Firestore: обновления сервера, правил и браузера должны быть согласованы. Отсутствие поколения в реестре не означает, что его безопасно удалить.

## Проверки и ограничения

[Тесты Firestore Emulator](../tests/integration) проверяют сбои промежуточной записи, конкурентную публикацию, гонки с удалением, очистку, аренды и изоляцию владельцев на синтетических данных. [Браузерные тесты](../tests/ui) проверяют реальный импорт через worker и жизненный цикл просмотрщика.

После построения сцены просмотрщик освобождает хранилище парсера, а при закрытии — управление, сцену, renderer и WebGL-контекст. Потоковой загрузки геометрии пока нет. Большие модели от разных экспортёров, замеры пиковой памяти и дисковый индекс метаданных остаются будущими задачами.
